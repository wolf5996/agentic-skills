# Resource-Watched Run

## Overview

- **Problem:** a single loaded Seurat object takes 2 to 5 times its on-disk size. A runaway job swaps the machine, fills the disk, or both, and the agent only finds out when the user complains.

- **Solution:** estimate peak memory before launch, run the job under `nice` and `/usr/bin/time` in the background, poll memory, swap and disk on an interval, alert or kill on a threshold breach, and report peak RSS and wall time when the job ends.

- **Rule:** never run a heavy job in the foreground. Never `sleep` in the foreground to wait for it. The job and its monitor both run in the background and wake the agent through notifications.

## When to Use

- Any job expected to take more than one or two minutes or more than 10% of RAM

- Conversions over many files where each file is loaded whole (`.Rda` to `.rds`, Seurat to Loupe, h5ad to h5seurat)

- Anything that writes multi-GB outputs to a disk that is not obviously empty

- Execute runners generated by `qmd-runner --mode execute`

## When NOT to Use

- Short jobs that finish in seconds; the pre-flight costs more than the job

- Cluster jobs with a scheduler (SLURM, SGE); request resources through `sbatch` or `qsub` instead

- Interactive exploratory sessions where the user is watching the console

## Workflow

### P0: Pre-flight

Check the machine and size the inputs before anything runs:

```bash
sysctl -n hw.memsize hw.ncpu          # bytes of RAM, cores
memory_pressure | grep percentage     # free memory now
sysctl -n vm.swapusage                # swap in use now
df -h <output-dir>                    # free disk on the volume that receives outputs
du -sh <input-dir>                    # total input size
ls -lS <input-dir> | head -3          # largest single input
```

Estimate peak memory:

| Workload | Rule of thumb |
|---|---|
| Load one compressed Seurat object | 2 to 5 times the file size (measured: 1 GB `.Rda` reached 4 GB RSS) |
| Process objects one at a time with `rm()` and `gc()` | peak = largest single object times the factor |
| Hold several objects at once | peak = sum of the objects times the factor |
| Gzip-compressed `.rds` output | about the same size as the gzip `.Rda` input |
| Uncompressed `.rds` output | 2 to 3 times the gzip input |

Stop and ask the user before launching when any of these hold:

- **Estimated peak above 60% of RAM:** the job may still fit, but the machine stops being usable

- **Disk headroom below 2 times the expected output:** a mid-run disk-full leaves truncated files

- **Free memory already below 40%:** something else is running; find out what first

Record a baseline so the post-run report has something to compare against:

```bash
df -k <output-dir> | awk 'NR==2{print $4}' > <scratch>/disk-before.txt
du -sk <output-dir> | cut -f1 > <scratch>/outdir-before.txt
ls -l <output-dir> | awk 'NR>1{print $5"\t"$9}' > <scratch>/sizes-before.tsv   # for conversions
```

### P1: Launch

```bash
nice -n 10 /usr/bin/time -l <command> > <log> 2>&1; echo "EXIT $?" >> <log>
```

Run this with the Bash tool in the background. Each part matters:

- **`nice -n 10` first:** applies to `time` and to every child, so the job yields CPU to the user's editor and browser

- **`/usr/bin/time -l`:** the shell builtin `time` has no `-l`; the full path gives peak RSS and wall time on stderr

- **`> <log> 2>&1`:** stderr carries R `message()` output and the `time` stats; both must land in the same log

- **`echo "EXIT $?" >> <log>`:** the sentinel the monitor waits for; without it the monitor never stops

### P2: Monitor

Launch this script in the background with `bash`, in the same turn as the job. It prints a line only when something happened: a progress line in the log, an error pattern, a threshold breach, every `EVERY` ticks, or the job ending.

```bash
#!/usr/bin/env bash
# Monitor a background job until its log ends with "EXIT <code>".
# LOG: job log; MATCH: regex for the job's command line; TARGET: path on the disk to watch.
LOG=${LOG:?}; MATCH=${MATCH:?}; TARGET=${TARGET:-$PWD}
RES=${RES:-${LOG%.log}-resources.log}
INTERVAL=${INTERVAL:-15}; EVERY=${EVERY:-20}
FREE_MIN=${FREE_MIN:-25}; DISK_MIN_GB=${DISK_MIN_GB:-50}; SWAP_GROW_MB=${SWAP_GROW_MB:-2048}
PROGRESS=${PROGRESS:-'chunk:|step|progress|done in'}
ERRORS=${ERRORS:-'Error|Execution halted|Killed|OOM|cannot allocate|Terminated'}

find_pid() {
  # pgrep -f also matches the zsh launcher, /usr/bin/time and this monitor's own shell.
  # The interpreter is the match with the largest RSS.
  local pids; pids=$(pgrep -f "$MATCH" | paste -sd, -)
  [ -n "$pids" ] && ps -o pid=,rss= -p "$pids" | sort -k2 -n | tail -1 | awk '{print $1}'
}

seen=$(wc -l < "$LOG"); tick=0; swap0=""
while true; do
  n=$(wc -l < "$LOG")
  if [ "$n" -gt "$seen" ]; then
    new=$(sed -n "$((seen + 1)),${n}p" "$LOG"); seen=$n
    printf '%s\n' "$new" | grep -E "$PROGRESS"
    printf '%s\n' "$new" | grep -E "$ERRORS" | sed 's/^/ALERT log: /'
  fi
  pid=$(find_pid)
  if [ -n "$pid" ]; then
    read -r rss cpu <<< "$(ps -o rss=,%cpu= -p "$pid")"
    rss_gb=$(awk -v r="$rss" 'BEGIN{printf "%.1f", r/1048576}')
  else rss_gb=none; cpu=0; fi
  free=$(memory_pressure | awk -F': ' '/free percentage/{gsub("%","",$2); print $2}')
  swap=$(sysctl -n vm.swapusage | awk '{print $6}' | tr -d M)
  disk_gb=$(df -g "$TARGET" | awk 'NR==2{print $4}')
  : "${swap0:=$swap}"
  line="$(date +%T) pid=${pid:-none} rss=${rss_gb}GB cpu=${cpu}% free=${free}% swap=${swap}M disk=${disk_gb}G"
  echo "$line" >> "$RES"; tick=$((tick + 1))
  alert=""
  [ "${free:-100}" -lt "$FREE_MIN" ] && alert="low memory"
  [ "${disk_gb:-999}" -lt "$DISK_MIN_GB" ] && alert="${alert:+$alert, }low disk"
  awk -v a="$swap" -v b="$swap0" -v g="$SWAP_GROW_MB" 'BEGIN{exit !(a - b > g)}' && alert="${alert:+$alert, }swap growing"
  if [ -n "$alert" ]; then echo "ALERT $alert: $line"; elif [ $((tick % EVERY)) -eq 0 ]; then echo "$line"; fi
  if grep -q '^EXIT' "$LOG"; then
    code=$(awk '/^EXIT/{print $2}' "$LOG" | tail -1)
    echo "DONE EXIT $code: $line"
    [ "$code" != "0" ] && grep -E "$ERRORS" "$LOG" | tail -3 | sed 's/^/  /'
    break
  fi
  sleep "$INTERVAL"
done
```

Invocation, as one background Bash call, in the same turn as the job so no log line is missed:

```bash
LOG=<scratch>/job.log MATCH='exec/R.*job.R' TARGET=<output-dir> bash <scratch>/monitor.sh
```

- **`INTERVAL` 15 to 30 s:** fine for jobs over a minute; 5 s only for short synthetic tests

- **`PROGRESS`:** match the job's own progress lines; `qmd-runner` execute runners print `chunk: <label>`

- **The monitor sleeps, the agent does not:** the loop runs in the background, so its internal `sleep` is allowed

- **Alerts are advisory:** the script prints `ALERT`; the agent decides whether to kill (P4). Nothing is killed automatically

### P3: Finding the right PID

`pgrep -f <script>` matches every process whose command line contains the script name. For `nice -n 10 /usr/bin/time -l Rscript job.R` that is four processes:

| Process | Command line | RSS |
|---|---|---|
| Launcher shell | `zsh -c ... Rscript job.R ...` | 3 MB |
| `/usr/bin/time` | `/usr/bin/time -l Rscript job.R` | 1 MB |
| R itself | `/Library/Frameworks/R.framework/Resources/bin/exec/R --no-echo --no-restore --file=job.R` | the real number |
| The monitor's own shell | `bash monitor.sh` with `MATCH='...job.R'` in its environment | 2 MB |

- **Rule:** take the match with the largest RSS. `find_pid()` above does this

- **Narrower `MATCH` helps:** `exec/R.*job.R` for R, `python.*job.py` for Python, `cellranger` for cellranger; confirm with `ps -o comm= -p <pid>`

- **`rss=0.0GB` on a running job means the wrong PID.** Fix the match before trusting any reading

### P4: Intervene

When an `ALERT` fires and the trend is bad (free memory falling tick after tick, swap growing, disk heading to zero):

1. `kill -TERM <pid>` on the interpreter PID from P3

2. Wait 10 to 15 s in the background (`for i in 1 2 3 4 5; do kill -0 <pid> 2>/dev/null || break; sleep 3; done`; macOS has no `timeout`), then `kill -KILL <pid>` if still alive

3. The log ends with `EXIT 143` (TERM) or `EXIT 137` (KILL); the monitor exits on its own

4. Tell the user what breached, what the readings were, and what was killed

5. Clean up partial outputs: the last progress line names the file being written; delete that file

6. Re-verify every output written during the run before trusting it

- **Gzip `.rds` warning:** a truncated gzip `.rds` can still read back as a valid object with wrong dimensions. Compare `dim()` of every object against the baseline table, not just the one that was being written

- **Resume:** with `qmd-runner` execute runners, regenerate with `--from <label>` at the first chunk whose inputs are complete on disk

### P5: Post-run report

Parse the log and the resources file:

```bash
exit_code=$(awk '/^EXIT/{print $2}' "$LOG" | tail -1)
real_s=$(awk '/ real /{print $1}' "$LOG" | tail -1)
max_rss_b=$(awk '/maximum resident set size/{print $1}' "$LOG" | tail -1)   # bytes on macOS
awk -v b="$max_rss_b" -v m="$(sysctl -n hw.memsize)" 'BEGIN{printf "peak %.1f GB (%.0f%% of RAM)\n", b/1073741824, 100*b/m}'
awk -F'free=' '{split($2,a,"%"); if (min=="" || a[1]<min) min=a[1]} END{print "free low-water " min "%"}' "$RES"
df -k <output-dir> | awk 'NR==2{print $4}'     # compare with disk-before.txt
du -sk <output-dir> | cut -f1                   # compare with outdir-before.txt
```

Report as a short table:

| Metric | Value |
|---|---|
| Exit code | `0` |
| Wall time | 12 min 51 s |
| Peak RSS | 4.9 GB (5% of RAM) |
| Free memory low-water | 94% |
| Swap | fell from 4.9 GB to 4.0 GB |
| Disk | 261 GiB to 252 GiB free; outputs 20.9 GB to 7.8 GB |
| Progress | 12 of 12 chunks |
| Log | `<scratch>/job.log` |

## Linux Equivalents

| macOS | Linux |
|---|---|
| `sysctl -n hw.memsize` | `free -b \| awk '/Mem:/{print $2}'` |
| `sysctl -n hw.ncpu` | `nproc` |
| `memory_pressure` free percentage | `free \| awk '/Mem:/{printf "%.0f", 100*$7/$2}'` (available over total) |
| `sysctl -n vm.swapusage` | `free -m \| awk '/Swap:/{print $3}'` |
| `/usr/bin/time -l` (RSS in bytes) | `/usr/bin/time -v` (`Maximum resident set size (kbytes)`, wall as `m:ss`) |
| `df -g` | `df -BG` |
| `ps -o rss=,%cpu=` | same (RSS in KB on both) |

## Common Mistakes

| Mistake | Fix |
|---|---|
| `pgrep -f` matched the launcher shell, so `rss=0.0GB` all run | Narrow `MATCH` to the interpreter and take the largest-RSS match |
| Foreground `sleep` while waiting for the job | Background the job and the monitor; let notifications wake the agent |
| Launched with `> log` but no `2>&1` | The `time` stats and R messages go to stderr; redirect both |
| No `echo "EXIT $?"` after the command | The monitor polls forever; always append the sentinel |
| Read `maximum resident set size` as kilobytes | On macOS `-l` reports bytes; divide by 1073741824 for GB |
| Trusted an `.rds` written when the job was killed | Compare dimensions against the pre-run baseline |
| Two heavy jobs at once | The estimates assume one job; serialise them |
| `df` on the wrong volume | Point `TARGET` at the output directory, not `$HOME` |
| `nice` after `time` | Works, but put `nice` first so the whole tree is niced |
